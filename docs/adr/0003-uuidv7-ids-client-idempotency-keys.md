# ADR-0003: App-generated UUIDv7 primary keys; client identifiers are idempotency keys only

**Status:** Accepted
**Accepted:** 2026-08-17
**Date:** 2026-08-17
**Supersedes:** none
**Superseded by:** none

## Context

`price_observations` and `receipt_lines` are the most insert-heavy tables in the system
and are append-only. Random UUIDv4 primary keys would scatter inserts across the B-tree, degrading
locality and inflating index maintenance.

The contributor app captures while offline and syncs later, which makes client-side identifier
generation superficially attractive: the client could name the resource it is creating.

Time-ordered identifiers embed a timestamp, which is visible to anyone holding one.

## Decision

Primary keys are UUIDv7, generated by the application through `core.ids.new_id()`,
with `uuidv7()` as the database-side default for fixtures and manual inserts.

Clients generate a `client_idempotency_key` only. It is an opaque UUIDv4, unique-indexed, used
solely for at-least-once sync deduplication. **It is never a primary key.**

Public surfaces use slugs. Internal UUIDs are never exposed on public read paths.

## Consequences

Insert locality is preserved on the tables where it matters most, and keyset
pagination on `(created_at, id)` is both correct and index-friendly (ADR-0004 pagination rules in
`04-api-contracts.md`).

A device with a skewed clock cannot corrupt the ordering, because it never generates a primary
key. A malicious client cannot craft identifiers arbitrarily far in the future.

The client keeps a local-only identifier and maps it to the server identifier on sync response,
which is a small amount of client-side bookkeeping.

Slugs must be generated for every user-visible entity, which is additional work at creation time.

## Alternatives considered

**UUIDv4 primary keys.** Rejected for insert locality on append-only hot tables.

**Client-generated UUIDv7 primary keys.** Rejected. Clock skew destroys the locality that
justified choosing v7 at all, and future-dated identifiers are craftable.

**Sequential integer keys.** Rejected. Enumerable, and they leak volume more directly than a
timestamp does.

**Exposing UUIDs publicly.** Rejected. Beyond stability concerns, time-ordered identifiers on a
public price page let an observer estimate submission volume, which is commercially sensitive
while coverage is thin.

## Revisit trigger

Never, absent a change in Postgres identifier support. The client-key distinction is
revisited only if offline sync semantics change fundamentally.
